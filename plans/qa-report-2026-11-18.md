## 3. Issues found and fixed

**Reduced motion was broken on the homepage.** `.page-home .aura` (specificity
0,2,0) sets a 2.4s animation; the reduced-motion override was a bare `.aura`
(0,1,0) and silently lost — on the only page that actually animates. The CSS
looked correct in the file. It was caught only by driving Chromium with
`reducedMotion:"reduce"` and reading computed `animationName`. Fixed with
`!important`; re-verified across all 16 pages.

This is the second specificity defect of exactly this shape today (the other was
`.case h3` beating `.cm-head`). Worth a standing habit: when a rule "looks
right" but does not take effect, diff computed styles rather than reading the
cascade.

## 5. Contrast — read this carefully

axe-core reports **no contrast violations**, and axe models rendered backgrounds
properly. That is the result I stand behind.

Separately, my own hand-rolled CSS-walking probe produced ten apparent failures.
**Every one I checked was a false positive**, and I checked them by sampling
actual rendered pixels:

- `.tab-em` highlights: background is painted by `::before`/`::after`, which the
  probe could not see. Ink on butter measures ~11.9:1.
- `.ct-stages` on courses: renders on dark plum (41,33,46) via a gradient, not
  the white the probe computed. Cream-on-dark ≈ 10.4:1.
- `.aow-card` on service-consulting: renders on near-white (254,252,250), not
  the deep magenta the probe computed.

The probe reads `backgroundColor` but not `background-image`, and this site's
backgrounds are layered gradients. **Do not trust a CSS-chain contrast probe on
this site.** Use axe, or sample pixels.

## 7. Architectural finding: why retrieval systems see both course states

Both the waitlist and the purchase markup ship in the HTML; CSS picks one at
runtime. For a browser this is correct and the inactive state is genuinely
unreachable. For a crawler or AI retrieval system that reads raw HTML without
executing CSS, **both states are visible in the source.** That fully explains the
symptom in the brief.

This is inherent to a static site with no build step (a constraint recorded in
`CLAUDE.md`). Options, in order of cost:

1. Leave it. Browsers and assistive tech are correct; only raw-HTML scrapers are
   confused.
2. Move the inactive state into a `<template>` element and clone it in JS when
   needed. Keeps the no-build-step rule, removes the inactive copy from parsed
   HTML. Modest change to two pages.
3. Introduce a build step that emits one state. Contradicts the current
   architecture.

My recommendation is (2) if this matters for AEO/GEO, but it is a real change
and I did not make it unasked.
